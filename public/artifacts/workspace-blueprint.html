Workspace Blueprint

A context-delivery system for AI agents. Three siloed workspaces — writing, production, community — each with its own routing, docs, and tools. An agent drops in, reads a CONTEXT.md, does its work, and exits without ever loading the wrong context.

01

Overview

Start Here

When you give an agent a task, it needs three things: what to do, how to do it, and what NOT to load. This blueprint solves the third problem with a 3-layer routing system, so each agent loads only the context it needs.

The problem why

Most teams either dump everything into one mega-prompt (wasting tokens, blurring focus) or scatter context across 30 files with no routing (the agent doesn't know what matters).

Without routing, agents lose the thread halfway through long tasks.
The solution how

Layered routing. CLAUDE.md shows the map. CONTEXT.md routes to a workspace. The workspace's own CONTEXT.md tells the agent exactly what to load and skip for each task type.

An agent writing a blog post never loads the deployment pipeline. An agent building code never loads voice guidelines.
02

The 3 Layers

Architecture

Each layer narrows the funnel. Together, they deliver only the context an agent needs for the task at hand.

Layer 1 · The Map

Always loaded

CLAUDE.md

The agent's GPS. Shows every folder, every ID system, every file placement rule. Load once at the start of every session.

Layer 2 · The Router

Top-level traffic cop

CONTEXT.md

"What's your task? Go here." Routes the agent to the right workspace and lists cross-workspace dependencies. Nothing more.

Layer 3 · The Workspace

Self-contained scope

workspace/CONTEXT.md

The detailed instructions live here — what to load, what to skip, when to invoke each skill, and what "done" looks like.

Why 3 layers? Token management. A single mega-doc wastes context on things the agent doesn't need. Layered routing keeps the funnel tight at every step.

Output: drafts/[slug]-[status].md moves through draft → review → final. A draft is review when structurally complete, final when voice and quality pass.

Skills wired in
  • /humanizer — Non-negotiable before any draft moves to final/. Catches AI-isms voice.md misses.
  • /doc-coauthoring — Long-form only (2000+ words). Tutorials, technical guides, whitepapers.
  • Web Search MCP — Research phase. Current data, competitor analysis, technical accuracy checks.
Voice essentials
  • Direct. Lead with the point, not the preamble.
  • Specific. Concrete examples over abstract principles.
  • Honest about tradeoffs. Name the downsides.
  • Conversational but not sloppy. Contractions yes, dated slang no.
Hard constraints: never leverage, utilize, or "In today's…". No emoji in technical content. No "It's worth noting that".

07

Production Pipeline

4 Stages

Four sequential stages. Each agent reads only the prior stage's output — no backtracking without explicit re-trigger. Skills accumulate as you move through the pipeline; an agent at Stage 02 never sees /frontend-design because it's not building yet.

Stage 01 01-briefs/

The Input

Finalized content from writing-room, copied here as the starting point. Says what to build and why, in plain language. Not a technical spec.

No tools input only
Stage 02 02-specs/

The Plan

Turns the brief into a buildable contract. Defines WHAT and WHEN, never HOW. Includes scope, acceptance criteria, dependencies — never line-by-line implementation.

Tools Context7 Web Search
Stage 03 03-builds/

The Work

Code, demos, assemblies. Builder reads the spec + reference docs, then has full creative freedom for implementation. Quality floor enforced by docs.

Tools /frontend-design /webapp-testing Context7
Stage 04 04-output/

The Deliverable

Finished, verified work. Versioned v1, v2, v3. Nothing lands here without passing the spec's acceptance criteria.

Tools /pdf /webapp-testing
The spec-as-contract pattern lets you swap agents between stages. The spec agent might be great at planning. The build agent might be great at code. Neither needs to understand the other's full context — just the spec.
Pipeline rule: Flow is forward. Briefs → specs → builds → output. Changes propagate forward — changed brief means regenerate spec; changed spec means rebuild.

Community

Workspace C

The distribution hub. Content from writing-room and deliverables from production get repurposed into newsletters, social posts, event materials. Same input → many outputs. Skills here are format-specific, not stage-specific.

Newsletter📧

500–800 words. Scannable. 3–5 sections max. Weekly cadence, Tuesday morning.

  • TL;DR at top
  • One primary CTA only
  • Personal but valuable tone
Twitter / X280

280 chars per tweet. Threads up to 10. Daily cadence.

  • One idea per tweet
  • Code screenshots > text-only
  • No hashtag stuffing
LinkedIn3000

3000 chars max. Front-load value. 2–3 posts per week (Tues/Wed/Thurs).

  • Hook in first line
  • Aggressive whitespace
  • PDF carousels perform well

11

Key Concepts

Mental Model

If you remember nothing else, remember these.

CONTEXT.md = the agent's entry point.md

Every workspace and sub-workspace has one. It answers: "You just landed here. Here's what this place is, what you can do, and what to load for each task." The README that agents actually read.

Workspaces are siloedsilo

Each workspace is a self-contained context. An agent in writing-room/ never needs to know what's in production/docs/. Cross-workspace flow happens through file handoffs, not shared context.

Docs ≠ workflowsplit

Reference docs (docs/) are stable knowledge loaded on demand — style guides, component registries, design systems. Workflow folders (workflows/) are the moving parts — stages, pipelines, active work. Separating them keeps loads tight.

File naming = state trackingstate

Instead of a database or PM tool, file names track progress. M1-outline.md exists? Module 1 is at outline stage. M1-script.md too? It's at script stage. Glance at a folder, know the status.

Skills are wired, not listedwire

A skill is 10x more useful when CONTEXT.md says when to invoke it, not just that it exists. "Run /humanizer before moving any draft to final/" beats "the humanizer skill is available."

MCPs extend the agent's reachmcp

MCP servers give agents new capabilities — web search, file conversion, API access. Like skills, they're most powerful when CONTEXT.md tells the agent when and where to use them.
